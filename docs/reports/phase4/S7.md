# AVG-S7 — presets, removal probe, crop, unselected photo

## Purpose

Four questions Phase 4 needs answered in Lightroom before rows 8 and 9 of the plan (`PHASE4_PLAN.md` row 4):

1. **Presets.** Is a preset made through `LrApplication.addDevelopPresetForPlugin`, or a preset file written by the plugin, visible in the Develop Presets panel before and after a restart, and does it apply?
   PHASES.md Phase 4, quoted: "`lr_create_preset_from_active` (mechanism spike first)." and "Acceptance: … a preset appears in the Develop Presets panel after Lightroom restart at most."
2. **Removal.** Is there an undocumented call that removes a photo from the catalog?
   PHASES.md Phase 4, quoted: "D-02 (open): how unpicked copies are removed; search for an SDK removal call first." PHASE4_PLAN decision 4 keeps unpicked copies in v1: "Revisit only if S7 finds a removal method."
3. **Crop.** After a crop on a virtual copy, do `getRawMetadata("width"/"height")` follow it?
   PHASES.md Phase 4, quoted: "`effective_scale` depends on whether `getRawMetadata("width"/"height")` follows a Lightroom crop [unverified]; test it on a cropped photo."
4. **Unselected photo.** Can the plugin write to and export a photo found with `findPhotoByUuid` without selecting it? (`lr_sync_series`, plan row 8.)

Design points:
- **The `.xmp` preset is a copy of a preset Jim makes by hand ("AVG S7 reference")**, with a new name and uuid, written next to it. That way neither the file format nor the folder is guessed [stated: Jim, 2026-09-27, chose this option over copying the plugin preset's file or writing a file from a remembered format].
- **Each run's two presets carry the run's date and time** ("AVG S7 plugin 20260927-143205", "AVG S7 xmp 20260927-143205"), and the preset file is never written over an existing file. A second run of menu item 1 therefore cannot replace or shadow the first run's presets; menu items 2 and 3 look presets up by the names in the state file (Greptile, PR #29).
- **Both copies are made from the selected original.** The original is re-selected before each one (P-09). The unselected write is Exposure2012 +0.5 EV.
- **Crop:** `CropLeft 0.1, CropRight 0.9, CropTop 0.2, CropBottom 0.8, CropAngle 0`, key names from `engine\src\params\sdk-keys.lrc15.json`. Writing all five replaces any crop or angle the copy inherited. `orientation` is read back too.
  - `summarize.ts` calls the crop comparison **inconclusive**, with the reason, if any of these holds: the orientation is not `"AB"` (the fixture's value in S5 [handle: same file, `orientation`]); the angle is not 0; the copy was cropped before; or the export's portrait/landscape differs from width × height (Greptile, PR #29).
- **The removal probe never calls what it finds** (`S7Probe.lua` header).
- **Photos are found again after the restart by uuid** (`findPhotoByUuid`), with a check of `copyName`.
  - The uuids are read from `s7_state.txt`, which menu item 1 writes. `LrPrefs` persistence across sessions is not documented [handle: https://lrc.mcor.dev/modules/LrPrefs.html, read 2026-09-27], so it is not used.
  - Removing the copies is called safe only when **every** copy menu item 1 made is found and selected, and nothing else (Greptile, PR #29).
- **`summarize.ts` pairs each observation with its run.** It takes the before/after files whose `state.run_at` equals the run's `run_at`. It counts files from other runs and leaves them out; if none matches, it reports "INCOMPLETE" (Greptile, PR #29).
- **The preset file takes its uuid from the file itself (fix after run 1, `fix/s7-xmp`).**
  - Run 1 wrote no preset file. For "AVG S7 reference", `preset:getUuid()` gave `221C89F4724E30813B7A73553BD53357`, but the file says `crs:UUID="94B7E167ED8FC14591B3B0CF685F6019"`. The harness looked for the first in the file, found nothing and stopped: "the reference file does not contain its uuid as text" [handle: `%TEMP%\LrC-AVG\S7\s7_run_2026-09-27T11-22-33.json` `presets.xmp`; line 7 of `%APPDATA%\Adobe\CameraRaw\Settings\AVG S7 reference.xmp`; both read by Claude Code 2026-09-27].
  - `S7Presets.writeXmp` now requires exactly one `crs:UUID` attribute in the reference file. It replaces that attribute alone, with a new uuid of the same form (32 hex digits, same case), and replaces the name. It records both uuids (`reference_uuid` from the SDK, `reference_file_uuid` from the file) and `sdk_uuid_is_file_uuid`.
  - **The re-run (menu items 4-6) writes only the preset file**: no copies, no photo changed. It keeps its own state file (`s7_xmp_state.txt`) and output files (`s7_xmp_run_*`, `s7_xmp_before_*`, `s7_xmp_after_*`), so nothing from run 1 is overwritten.
  - Items 5 and 6 also record the file preset's settings against the reference's (`xmp_vs_reference`), and whether the file on disk is still byte for byte what item 4 wrote (`file_on_disk.same_as_written`, else `first_different_line`): did Lightroom rewrite it?
    - Item 4 keeps a copy of what it wrote (`s7_xmp_as_written_<time>.xmp`, in `%TEMP%\LrC-AVG\S7\`; `summarize.ts` does not copy it) to compare against. Size and uuid alone would miss a rewrite that changes a setting (Greptile, PR #30).
  - `summarize.ts` reports the re-run as `item1_presets.xmp_rerun`, paired by its own `run_at`.
  - For the file preset, `found_by_uuid` tries `developPresetByUuid` with the uuid written in the file (`uuid_kind: "file"`). After run 1, whether the SDK takes that uuid is [unverified].

## Pre-run findings (Claude Code)

- **SDK reference pages** [handle: lrc.mcor.dev, read 2026-09-27]:
  - `addDevelopPresetForPlugin(plugin, presetName, presetValue)` "Adds a preset hidden within a plug-in. These presets are stored in a special folder called 'Plugin Develop Presets.'" (SDK 3.0). `getDevelopPresetsForPlugin`, `developPresetFolders` and `developPresetByUuid` are on the same page (https://lrc.mcor.dev/modules/LrApplication.html).
  - `LrDevelopPresetFolder` has `getDevelopPresets`, `getName`, `getPath` and no create call. `LrDevelopPreset` has `getFile`, `getName`, `getParent`, `getSetting`, `getUuid`.
  - `photo:applyDevelopPreset(preset, plugin, …)` must run inside a write gate (https://lrc.mcor.dev/modules/LrPhoto.html).
