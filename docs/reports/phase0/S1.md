# AVG-S1 — preview freshness + latency

> Status note: runs 1 and 2 are observed (see "Run 1 analysis" and "Run 2 analysis"). Verdict (Jim, 2026-09-24): **no-go for thumbnails; export is the primary preview path.**

## Purpose

After `photo:applyDevelopSettings`, is `photo:requestJpegThumbnail(1600, …)` fresh (it reflects the change) and fast? How does an `LrExportSession` 1600 px JPEG compare?
PHASES.md rule, quoted: "Go: fresh preview ≤ 1.5 s. Conditional: fresh but > 1.5 s → export fallback becomes primary. No-go: stale → export path only, and the pass budget is re-baselined."

## Run 1 analysis (Claude Code, 2026-09-23)

Sources: Jim's run-1 output above, the raw `%TEMP%\LrC-AVG\s1_results.csv` from that run, and the done-dialog screenshot `spikes\S1\Screenshot_2026-09-23 193913.jpg`.

- **The errors came from Lightroom, not `measure.ts`.** For each of the 5 steps, `photo:requestJpegThumbnail(1600, nil, cb)` issued right after `applyDevelopSettings` got a callback within 0.0–0.5 ms with **no JPEG data and the error string `error loading thumb`** (CSV `error` column). No second callback arrived in the following 2 s. `measure.ts` only reported that column.
- **The harness hid it.** The run-1 done dialog printed "first callback 0 ms (1 callback)" without the error, which is why Jim saw "no errors" in Lightroom. Fixed in the retry harness: failures are now marked FAILED in the dialog, with an ERRORS headline.
- **The develop writes worked.** The `Exposure2012` read-backs alternate `0.33 → 1.33 → 0.33 → 1.33 → 0.33 → 1.33` as intended, and `applyDevelopSettings` took 20–31 ms per step.
- **Thumbnails work when nothing changed.** Baseline: 118 ms, 1890×1260 (larger than the 1600 px requested, consistent with "sizes are minimums"), 853,783 B, no ICC profile, mean luma 91.44. `requestJpegThumbnail(1600, nil, …)` accepts a nil height.
- **The export works right after changes, and is fresh.** 2588 ms, 1600×1067, 727,872 B, with an embedded ICC profile (3144 B). Mean luma 119.86 against the baseline thumbnail's 91.44, taken at exposure 1.33 (+1 EV) vs 0.33. So the export reflected the latest develop state [inference: brightness direction only; the two images come from different pipelines]. The byte size means `LR_jpeg_quality = 0.75` was *not* read as quality 0.75 on a 0–100 scale, which would give a tiny file. Whether the range is 0–1 is still [unverified].
- **The image is fine.** The same NEF produced a baseline thumbnail and an export; the failure is tied to requesting a thumbnail immediately after a develop change. No need to switch images.
- **What run 1 does not answer:** how long after a change a thumbnail becomes available, and whether that thumbnail is fresh. Rerunning the same harness would repeat the error, so the harness now re-requests every 50 ms until data arrives (30 s cap per step) and records `attempts`, `first_error` and `ready_ms` (time from the write returning to the first usable thumbnail). Run 2 uses that harness on the same photo.
- The `measure.ts` verdict printed in run 1 ("no-go … stale preview seen") was wrong: there were no images to be stale. `measure.ts` now reports "NO IMAGE" and "incomplete" in that case. Re-run on the run-1 files it prints: `suggested verdict: incomplete — 5 of 5 step(s) produced no thumbnail (see NO IMAGE lines); no verdict from this run`.

## Run 2 analysis (Claude Code, 2026-09-24)

Sources: Jim's run-2 output above, the raw `%TEMP%\LrC-AVG\s1_results.csv` of run `20260923-205042`, and the done-dialog screenshot `docs\reports\phase0\S1-run2-dialog.png`.

- **After a develop change, `requestJpegThumbnail` never delivered an image within 30 s.** Each of the 5 steps made 482–487 requests (one about every 62 ms). Every one was answered at once with no data and `error loading thumb`, and none returned an image before the 30 s cap. This happened with Lightroom freshly restarted and the photo open in Develop. The dialog also shows 0 requests left unanswered, so no callback was lost.
- **Even without a change, the thumbnail is not a dependable 1600 px source.** The run-2 baseline came back at **945×630** for a 1600 px request, while run 1's baseline was 1890×1260. LR_SDK_NOTES quotes the SDK page "Request sizes are treated as minimums"; on LrC 15.5.1 the returned size appears to depend on whatever preview Lightroom has cached (run 2 came right after a restart) [inference from two runs].
- **The export path is fresh and repeatable.** 2587 ms vs 2588 ms in run 1; the same 1600×1067 size, the same 727,872 bytes and the same mean luma 119.86 (+28.4 vs baseline at +1 EV). The SHA differs, presumably from embedded export metadata such as a timestamp [inference].
- `applyDevelopSettings` is cheap: 21–43 ms per write.
- `LrDate.currentTime()` has sub-millisecond resolution on Windows [observed: CSV values such as 26.4 ms and 42.6 ms], which resolves that pre-run `[unverified]`.
- The export byte size matched between runs. `LR_jpeg_quality = 0.75` is evidently not read as 0.75 on a 0–100 scale (that would give a tiny file). Whether its range is 0–1 remains [unverified].
- **What this means against the PHASES.md rule:** the thumbnail path gave no usable post-change image, which is worse than "stale". The rule's no-go consequence is "export path only, and the pass budget is re-baselined". The export takes about 2.6 s at 1600 px, which is over the 1.5 s pass-budget target. The verdict is Jim's; the options are presented in the PR and the session.

## Verdict

**No-go for `requestJpegThumbnail`; `LrExportSession` export is the primary preview path.** Decided by Jim on 2026-09-24 [stated: Jim chose "No-go; export is primary" when asked in the Claude Code session]. Basis: runs 1 and 2 above. No post-change thumbnail arrived within 30 s (5/5 steps), the no-change thumbnail came back undersized (945×630 for a 1600 px request), and the export was fresh and repeatable at about 2.6 s for 1600 px.

## Consequences / open questions

Per the PHASES.md no-go rule ("export path only, and the pass budget is re-baselined"):

1. **Preview pipeline (ARCHITECTURE §6, PRD §6.8):** the export becomes the primary source rather than the fallback. `render_preview` via `requestJpegThumbnail` and its "retry once, then export" freshness dance are dropped for the post-change preview. The `preview_source: thumbnail | export` field becomes `export` in practice. These are proposed changes to the architect's vault docs; Claude Code has not edited them.
2. **Pass budget (PRD §2 goal, NFR-2):** re-baseline from "≤ 1.5 s per pass, 400 ms render" to about **3 s per pass local**: ~2.6 s export at 1600 px, ~20–45 ms `applyDevelopSettings`, plus metrics and transport (not yet measured). A 4-pass session then spends about 12 s in local work. That is expected to stay small next to Claude's per-pass thinking time [inference; to be measured in Phase 2].
3. **Open, for Phase 2 (not Phase 0):** export time at a smaller long edge (e.g. 1024–1280 px), to see how much of the 2.6 s scales with size; and whether the export's embedded ICC profile (3144 B) needs handling in the metrics (sharp converts to sRGB on decode [unverified for this profile]).
4. **LR_SDK_NOTES "To record in Phase 0":** measured `requestJpegThumbnail` latency and freshness after `applyDevelopSettings` → "no image within 30 s; immediate `error loading thumb`; no-change thumbnails are not size-guaranteed (945×630 for a 1600 px request)". To be written into the vault notes when Phase 0 closes.
