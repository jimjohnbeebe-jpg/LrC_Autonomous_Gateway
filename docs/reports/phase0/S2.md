# AVG-S2 — LrSocket dual socket

## Purpose

Can the plugin listen with `LrSocket.bind` `mode="receive"` on 8765 and `mode="send"` on 8766, the engine connect to both, and messages up to at least 1 MB round-trip intact? What is the RTT?
PHASES.md rule, quoted: "Go: both directions work, ≥ 1 MB messages pass. No-go: adopt HTTP polling fallback at ≤ 250 ms active."

## Harness

`plugin\spikes\S2.lrplugin\{S2Server,S2Start,S2Stop,S2Status}.lua`, `spikes\S2\client.ts`; how to run: `spikes\S2\README.md`.

## Pre-run findings (Claude Code)

- **The transport pattern is proven upstream** [handle: `docs\AUTOMAAT_SURVEY.md` §4.3, §6]: Automaat has used exactly this topology (plugin `receive` + `send` listeners, Node TCP client, `\n`-framed JSON) since upstream commit `3ef5d72` (2026-05-06), on ports 58763/58764. The LR_SDK_NOTES claim that "LrSocket does not support server sockets" and "3 s HTTP polling" is stale: the polling was removed in that commit. Message-size limits and RTT were never measured upstream.
- `client.ts` was checked against a fake Node echo server that mimics the plugin's protocol, with a simulated 3 MB line cap. Result: hello OK (2.0 ms), 20 pings OK, 1 MB OK (17.3 ms), 2 MB OK, 4 MB → "no echo within 5000 ms", reported as "largest message that survived: 2097152 chars" [handle: fake server + `node spikes\S2\client.ts --max-mb 8 --timeout-s 5`, Phase 0 transcript]. These are **Node-to-Node numbers, not Lightroom's**. The stray result file from that run was deleted from `%TEMP%\LrC-AVG`.
- `S2Server.lua` parses as Lua 5.1. Behaviour inside Lightroom is unverified.
