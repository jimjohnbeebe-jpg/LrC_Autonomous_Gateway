# AVG-S9: the Tauri HUD shell validation

## Purpose

Phase 7 replaces the LrView HUD with a window in its own process. Jim chose Tauri v2, pinned to 2.12.x (spec D2; vault AVG-013) [stated: Jim, 2026-10-04: "We chose Tauri because it is a high performer with a small footprint … performance and appearance are all important, as well as deployability"]. ## Harness

How to run it: [`spikes\S9\README.md`](../../../spikes/S9/README.md). In short, Jim runs one command, `node spikes\S9\measure.ts`, with Lightroom open in Develop and Claude Desktop open.

- `spikes\S9\stub-engine.ts`: stands in for the HUD channel of spec 3.3, listening on 127.0.0.1 only. It writes `%USERPROFILE%\.lrc-avg\hud_endpoint.json` with `port`, `token`, `pid`, `engine_version` and `written_at`. It checks the HUD's 32-byte token in constant time, sends the scripted states W, V and C, and pings every 2 s. It uses no Claude and no Lightroom.
- `spikes\S9\channel.ts`: the messages as zod schemas, shared by the stub and the HUD's UI.
- `spikes\S9\tauri\`: a minimal Tauri 2.12.1 app. Its frameless, initially hidden window shows the collapsed Deck bar, adapted from `docs\hud\option-c\option-c.html`. The TypeScript UI holds the WebSocket client (spec D2, "Contract reuse"). Rust (`src-tauri\src\win.rs`):
  - shows and hides through Win32 with `ShowWindow` `SW_SHOWNA` / `SW_HIDE`, never Tauri's `show()`/`hide()`;
  - makes the window topmost only while Lightroom or the HUD is in front, via `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`, and otherwise places it just below the foreground window;
  - follows Lightroom's main window through `EVENT_OBJECT_LOCATIONCHANGE` and the minimise events;
  - exits when Lightroom's process exits.
  
  `webview.rs` also sets WebView2's `IsVisible` and `MemoryUsageTargetLevel` on every hide and show (see the pre-run findings). The HUD logs to `%TEMP%\LrC-AVG\S9\hud_<pid>_<start ms>.jsonl`.
- `spikes\S9\win32.ts`: reads, through koffi, the foreground window, window rectangles, `IsWindowVisible`, the z-order and the topmost style, and private bytes and CPU times over the HUD's process tree.
- `spikes\S9\measure.ts`, `auto.ts`, `jim.ts`, `summary.ts`, `harness.ts`: the run itself.
  - Part 1 is hands-off: S9-1 to S9-5 and the programmatic half of S9-6.
  - Part 2 is Jim's steps: S9-6, S9-7, S9-8, S9-11, S9-9 and S9-10, in that order, because S9-10 quits Lightroom.
  - S9-12 is read from the build output.
  - Everything goes to `%TEMP%\LrC-AVG\S9\s9_<run>.json`, with a summary marked as a suggestion.
- `spikes\S9\prereqs.ps1`: checks rustup (MSVC), the C++ Build Tools, WebView2 and Node, and prints each install step with its handle.
- Build: `npm run s9:build -w spikes`. Claude Code built the HUD on Jim's machine; the build output is gitignored.

Design points:
- **Transport.** WebSocket on 127.0.0.1, one JSON message per frame, in place of spec 3.3's newline-delimited TCP. A WebView page cannot open a raw TCP socket [inference]. The endpoint file, handshake and message names are 3.3's [stated: Jim, 2026-10-04, "Use recommendations for websocket"]. The server is `ws` 8.22.0.
- **The UI's contract.** The UI validates every message with the same zod 4.6.5 schemas as the stub. `build-ui.ts` strips the TypeScript types with Node's `module.stripTypeScriptTypes` and copies zod's ESM files beside it, with no bundler.
- **"Visible and painted".** S9-1 and S9-2 take the later of the first `IsWindowVisible` true, polled every 1-2 ms with a 1 ms timer resolution, and the paint time. The paint time is taken in the first `requestAnimationFrame` after the render, as spec D2 says. A paint alone does not prove visibility (pre-run finding 3).
- **The stub starts the HUD detached, without `windowsHide`.** The detach is spec 3.2 and E8. `windowsHide` would put SW_HIDE in the HUD's STARTUPINFO, which could affect its first `ShowWindow` [inference]. Whether the engine (row 2) can pass it is [unverified].
- **Placement.** The bar sits over the bottom 144 px of Lightroom's client area (the filmstrip band on the mockup stage), 44 px tall, both scaled by Lightroom's DPI [stage]. Lightroom's real filmstrip height is [unverified] (spec 13.2, item 26). S9-8 asks Jim, outside the gate, where the bar landed.
- **Lightroom's identity.** Lightroom is found as the largest visible top-level window of the process whose image is `Lightroom.exe`. The name is [unverified] (spec 13.2, item 11), and the run records it. Claude Desktop is found as a `claude.exe` process that owns a visible window: a `claude.exe` that owned no window also ran on this machine, the Claude Code CLI [inference] [handle: `docs\reports\phase7\S9-prerun\prerun.txt` section 8].
- **S9-10 watches Lightroom's process, not its main window.** That is stricter than spec 3.2's "main window is gone".
- **A dev override.** `LRC_AVG_S9_LR_EXE` makes another program stand in for Lightroom, for Claude Code's dry runs. Jim's run does not set it.

## Pre-run findings (Claude Code)

All from Claude Code's runs on Jim's machine, with Lightroom not running. They are not gate results. The full output and every driver script, verbatim, are in [`docs\reports\phase7\S9-prerun\prerun.txt`](S9-prerun/prerun.txt).

1. **Toolchain.** `prereqs.ps1` found everything after Claude Code installed rustup 1.29.1 [stated: Jim, 2026-10-04, "Yes, please install software as needed"]: rustc 1.99.0 MSVC, the C++ Build Tools 2022, WebView2 154.0.4258.53 and Node v24.11.1 [handle: prerun.txt section 1].
2. **Build.** Tauri 2.12.1 (crate `=2.12.1`, tauri-build `=2.7.1`, webview2-com `=0.39.1`) built with the release profile from Tauri's size guide [handle: `https://raw.githubusercontent.com/tauri-apps/tauri-docs/v2/src/content/docs/concept/size.mdx` lines 27-31]. The exe is 3,442,176 B and the NSIS installer 1,387,211 B [handle: prerun.txt section 2]. These sizes are S9-12's inputs; measure.ts reads them again at the run.
3. **The channel works end to end.** The WebView's origin is `http://tauri.localhost`, the token handshake is accepted, states render, and the stub deletes the endpoint file when it quits. One paint arrived 6 ms before the HUD logged its show, so measure.ts takes the later of the two [handle: prerun.txt section 3].
4. **A Win32 hide alone left WebView2 rendering.** With only `SW_HIDE`, the pulsing ring cost 9.37 % of a core while hidden (9.99 % visible) [handle: prerun.txt section 5a]. The HUD now also sets the WebView2 controller's `IsVisible` [handle: https://raw.githubusercontent.com/MicrosoftDocs/edge-developer/main/microsoft-edge/webview2/concepts/overview-features-apis.md line 3081, "The visibility of WebView2 can be toggled using `IsVisible`"] and `MemoryUsageTargetLevel` Low when hidden, Normal when shown [handle: …/concepts/performance.md line 242]. Hidden and pulsing then cost 0.31 % [handle: prerun.txt section 5b]. Neither call is Tauri's `show()`/`hide()`, so the D2 rule holds [inference]. This is the risk spec D2 named ("tao's own visibility flag no longer matches the window"), seen here as WebView2's.
5. **The pulse's cost depends on how it is drawn.** Measured visible and pulsing, over 15 s: an SVG opacity animation 9.99 %; a composited HTML opacity animation 10.94 %; a CSS `steps()` border-colour animation 5.94 %; a 200 ms timer stepping the colour, 8 steps per 1.6 s loop, 1.35 % [handle: prerun.txt sections 5a-5d]. The build uses the timer. The pulse still loops in 1.6 s (spec 8.4), in 8 steps rather than a smooth ease.
6. **The measuring process must be DPI aware.** On a 150 % monitor, the non-aware Node process read the stand-in's client area as 1359 px wide where the HUD read 2039 (×1.5), so a correctly placed bar looked misplaced [handle: prerun.txt section 6]. `win32.ts` now calls `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`. After that, the bar was in place at start, in place 15.8-43.7 ms after a move made from code, hidden 15.4 ms after a minimise, and shown in place 42.0 ms after a restore; the foreground and location hooks fired [handle: prerun.txt section 6].
7. **Last dry run of Part 1** (Notepad standing in, VS Code in front, not Jim's machine state) [handle: prerun.txt section 7]:
   - S9-1 median 530.6 ms.
   - S9-2 p95 14.8 ms.
   - S9-3 p95 1.2 ms.
   - **S9-4: 158.1 MiB over the tree (host 6.1 MiB), over the 150 MiB target.**
   - **S9-5: 0.62 % hidden and 2.32 % visible, both just over target.**
   - 20 of 20 programmatic shows left the foreground unchanged.
   
   Memory varied between runs, from 155.7 to 198.5 MiB for the same states [handle: prerun.txt section 5]. So S9-4 and S9-5 are likely to be decided near their limits on Jim's run [inference].
   After Greptile's review of PR #80, the gates count a sample only in the window state it was meant to measure, and a CPU or memory sample only when every process of the tree was read for the whole window. Across the dry runs, hidden CPU read 0.44-0.62 % (limit 0.5 %) and the hidden tree 154.8-161.1 MiB (limit 150 MiB) [handle: prerun.txt sections 7, 10 and 11]: S9-4 runs over and S9-5 sits at its limit.
8. **For row 4, contract reuse.** `engine\src\bridge\hud-protocol.ts:57` measures text with `Buffer.byteLength`, which a WebView page does not have [inference: Buffer is a Node API]. The HUD app's shared schemas need `TextEncoder` there. S9's `channel.ts` keeps its own schemas for this reason.
9. **Windows reused a HUD's pid across runs.** The HUD's log, named by pid, had appended an earlier process's lines, so the harness polled an old window and S9-1 missed one run [handle: prerun.txt section 10a]. Each HUD process now logs to its own file, named by pid and start time, and the harness reads only a file started after the spawn.

## S9b re-run

**Why:** S9-4 and S9-5 failed narrowly, S9-8 recorded nothing because of the prompt, and the bar trailed Lightroom during drags (Jim's note, "Observed").

**What changed** (README "S9b re-run"; evidence `docs\reports\phase7\S9b-prerun\prerun.txt`):
- **The bar hides during drags and resizes** (`spikes\S9\tauri\src-tauri\src\drag.rs`). The primary trigger is `EVENT_SYSTEM_MOVESIZESTART`/`END` for Lightroom's window; whether Lightroom sends them is [unverified], and the re-run records it (`s9_8.move_events`). The fallback trigger is a burst: 3 events within 200 ms of each other, each changing the rectangle, then shown after 150 ms of quiet. A burst therefore shows the bar about 150 ms after a move ends, over the 100 ms target [handle: prerun.txt section 4b].
- **WebView2 runs without its GPU process.** `tauri.conf.json` `additionalBrowserArgs` keeps wry's default `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection` and adds `--disable-gpu` [handle: `tauri-utils` 2.10.1 `src/config.rs:2124-2133`, the `additionalBrowserArgs` doc comment: "By default wry passes … so if you set this, you also need to disable these components by yourself"]. That `--disable-gpu` removes the GPU process is observed [handle: prerun.txt section 2, 7 processes and no GPU-sized one]; its effect on how the text looks is Jim's to judge (a non-gate question).
- **`TrySuspend` was tried and dropped.** It saved nothing, and a suspended page never heard the next state, so the HUD could not show itself [handle: prerun.txt section 1; MS performance.md:244, "pauses scripts"].
- **S9-8:** Enter first, then Enter again when done. Each episode records the time visible out of place (`detached_ms`, gated at ≤ 100 ms) and Lightroom's own rectangle changes (`lr_changes`). Two questions are added: the drag question (gated) and a sharpness question (not a gate).
- **`--s9b`** runs Part 1 and S9-8 only. S9-6, S9-7, S9-9, S9-10 and S9-11 stand from run 1.
