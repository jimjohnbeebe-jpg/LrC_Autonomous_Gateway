# AVG-S7 — presets, removal probe, crop, unselected photo

## Purpose

Four questions Phase 4 needs answered in Lightroom before rows 8 and 9 of the plan (`PHASE4_PLAN.md` row 4):

1. **Presets.** Is a preset made through `LrApplication.addDevelopPresetForPlugin`, or a preset file written by the plugin, visible in the Develop Presets panel before and after a restart, and does it apply?
   PHASES.md Phase 4, quoted: "`lr_create_preset_from_active` (mechanism spike first)." and "Acceptance: … a preset appears in the Develop Presets panel after Lightroom restart at most."
2. **Removal.** Is there an undocumented call that removes a photo from the catalog?
   PHASES.md Phase 4, quoted: "D-02 (open): how unpicked copies are removed; search for an SDK removal call first." PHASE4_PLAN decision 4 keeps unpicked copies in v1: "Revisit only if S7 finds a removal method."

   PHASES.md Phase 4, quoted: "`effective_scale` depends on whether `getRawMetadata("width"/"height")` follows a Lightroom crop [unverified]; test it on a cropped photo."
4. **Unselected photo.** Can the plugin write to and export a photo found with `findPhotoByUuid` without selecting it? (`lr_sync_series`, plan row 8.)

Design points:
- **The `.xmp` preset is a copy of a preset Jim makes by hand ("AVG S7 reference")**, with a new name and uuid, written next to it. That way neither the file format nor the folder is guessed [stated: Jim, 2026-09-27, chose this option over copying the plugin preset's file or writing a file from a remembered format].
- **Both copies are made from the selected original.** The original is re-selected before each one (P-09). Crop: `CropLeft 0.1, CropRight 0.9, CropTop 0.2, CropBottom 0.8`, key names from `engine\src\params\sdk-keys.lrc15.json`. The unselected write is Exposure2012 +0.5 EV.
- **The removal probe never calls what it finds** (`S7Probe.lua` header).
- **Photos are found again after the restart by uuid** (`findPhotoByUuid`), with a check of `copyName`. The uuids are read from `s7_state.txt`, which menu item 1 writes; `LrPrefs` persistence across sessions is not documented [handle: https://lrc.mcor.dev/modules/LrPrefs.html, read 2026-09-27], so it is not used.

## Pre-run findings (Claude Code)

- **SDK reference pages** [handle: lrc.mcor.dev, read 2026-09-27]:
  - `addDevelopPresetForPlugin(plugin, presetName, presetValue)` "Adds a preset hidden within a plug-in. These presets are stored in a special folder called 'Plugin Develop Presets.'" (SDK 3.0). `getDevelopPresetsForPlugin`, `developPresetFolders` and `developPresetByUuid` are on the same page (https://lrc.mcor.dev/modules/LrApplication.html).
  - `LrDevelopPresetFolder` has `getDevelopPresets`, `getName`, `getPath` and no create call. `LrDevelopPreset` has `getFile`, `getName`, `getParent`, `getSetting`, `getUuid`.
  - `photo:applyDevelopPreset(preset, plugin, …)` must run inside a write gate (https://lrc.mcor.dev/modules/LrPhoto.html).
  - `catalog:findPhotoByUuid` (SDK 2.0) must run in a task (https://lrc.mcor.dev/modules/LrCatalog.html).
  - No method on the LrCatalog or LrPhoto page removes a photo. The only removal-like names are `deleteAllEmptyMasks`, `deleteDevelopSnapshot`, `deleteSmartPreview` and `removeKeyword`.
  - `getRawMetadata` lists `width`/`height` ("of the original source photo"), `dimensions`, `croppedDimensions` and `isCropped` (LrPhoto page).
- **Automaat** reports its plugin presets as not visible in Develop (`visible_in_develop = false`) [upstream claim: `vendor\automaat\plugin\LightroomMCP.lrplugin\HandlerDevelop.lua:600`]. Not observed by us.
- **Where Develop presets live on this machine** is [unverified]: Adobe's page on file locations returned HTTP 403 to Claude Code (https://helpx.adobe.com/lightroom-classic/kb/preference-file-and-other-file-locations.html, 2026-09-27). Menu item 1 records the folders Lightroom reports (`folder:getPath()`, `preset:getFile()`).
  - Before the run, `%APPDATA%\Adobe\CameraRaw\Settings\` held one `.xmp` ("Painted Hills LUT.xmp"), and `%APPDATA%\Adobe\Lightroom\Develop Presets\{Lightroom Presets,User Presets}` were empty [handle: `ls` and `find` by Claude Code, 2026-09-27].
  - So no hand-made user preset existed to copy, which is why the run starts by making "AVG S7 reference".
- **Syntax:** 11/11 Lua files in `plugin\spikes\S7.lrplugin` parse as Lua 5.1 [handle: Claude Code, scratch install `luaparse@0.3.1` (not a project dependency), `luaparse.parse(src, { luaVersion: "5.1" })`, 2026-09-27]. That proves syntax only.
- **Smoke run against a fake Lightroom:** the whole flow (menu item 1, item 2, then item 3 after a simulated restart) ran under `fengari@0.1.4`, a Lua 5.3 VM, against a stub of every SDK call the harness makes [handle: Claude Code session 2026-09-27, scratch files outside the repo].
  - Scenarios: all calls succeed; no reference preset; `createVirtualCopies` fails; `addDevelopPresetForPlugin` needs a write gate; Jim clicks Cancel.
  - In each, the harness finished without a Lua error and recorded the outcome:
    - no reference: it stops before changing anything;
    - failed copies: items 3 and 4 FAILED, the presets still made;
    - gate: `how: "inside withWriteAccessDo"` with the first error kept;
    - Cancel: "NOT ANSWERED".
  - The stub's behaviour is Claude Code's invention, so this shows the Lua runs and records what it is given, and **nothing about Lightroom**.
- **`summarize.ts`** ran on the smoke run's files, with sharp-made JPEGs in place of the exports [handle: same session].
  - It found the exports under the source folder when their recorded folder had moved.
  - It copied 5 files and not the JPEGs.
  - With the real user folder planted 18 times in the 5 files (JSON-escaped in mixed case, raw, and with forward slashes), 0 remained in the copies (`grep -ril` found none).
