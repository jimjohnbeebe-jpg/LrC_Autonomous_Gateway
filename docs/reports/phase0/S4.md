## Analysis (Claude Code, 2026-09-26)

Every statement below comes from `docs\reports\phase0\S4\s4_result_2026-09-26T09-57-16.json`, unless it carries another handle or tag.

- **The floating HUD is non-modal.** Jim could drag the Exposure slider while it was open (`slider_draggable`), and the drag registered: Exposure read −0.49 when the HUD closed, against 0.33 at the start.
- **It updates live, including during a drag.** Labels bound with `LrView.bind` to a `LrBinding.makePropertyTable` table (`plugin\spikes\S4.lrplugin\S4Hud.lua:67-77`) changed as a separate task wrote them once per second (`S4Hud.lua:82-94`). The counter kept counting while Jim dragged the slider (`ticks_while_dragging`). How smoothly each second's change appeared was not measured.
- **Develop kept the keyboard.** With the HUD open and updating, `\` switched Before/After (`backslash_toggled`), and G then D switched to Library and back (`hud_survived_module_switch`, which presupposes the module switch happened [inference]). In the README, Jim clicked the photo before pressing `\` (step 6) and clicked the main window before G/D (step 7). So this shows that the HUD's per-second updates did not take the keyboard away from the main window. It does not show whether the HUD takes focus at the moment it opens; that was not tested.
- **It stays on top and survives a module switch.** The HUD stayed in front after Jim clicked the main window (`hud_stayed_in_front`) and was still there after Library and back (`hud_survived_module_switch`).
- **With `blockTask = true`, `presentFloatingDialog` blocks the calling task until the window closes.** The call (`S4Hud.lua:97-104`) returned after 36.65 s, with `windowWillClose` already fired (`window_open_when_call_returned: false`). Meanwhile the updater, started as its own task before the call, kept running and finished at 09:56:58. This settles the pre-run unknown for `blockTask = true`. The behaviour without `blockTask` was not tested.
- **The develop write-back worked.** Exposure went back from −0.49 to 0.33 through `applyDevelopSettings` inside `withWriteAccessDo`, called after the HUD closed, and read back equal (`restored: true`).
- Context: the Lightroom process that ran S4 had been running since 2026-09-24 20:52:03, so it was not restarted for this spike [handle: `Get-Process Lightroom` → `StartTime 9/24/2026 8:52:03 PM`, run by Claude Code on 2026-09-26 just after the run].

## Consequences / open questions

<!-- PRD §6.3 HUD design; Phase 5 scope. -->
Proposed changes; none has been applied to the vault docs. They are for the architect (Jim).

- **PRD §6.3 (`PRD.md:98-100`): the floating, non-modal, live-bound HUD is feasible as designed.** Its `[unverified: focus/refresh behaviour on Windows]` can cite this report.
- **LR_SDK_NOTES LrDialogs (`LR_SDK_NOTES.md:39`):** record for LrC 15.5.1 on Windows 11 (version [stated: Jim, 2026-09-22, vault `LrC_AVG_STATE.md` "Environment"]; the S4 file does not record it) that a floating dialog stays non-modal and on top of the main window, survives module switches, and updates live through `LrView.bind` on a property table. Also record that `blockTask = true` blocks the calling task until the window closes while other tasks keep running.
- **Phase 5 HUD design (ARCHITECTURE §1 `Hud.lua`):** present the HUD from its own task. With `blockTask = true` that task is parked until the HUD closes, so the bridge loop and the updates must run in other tasks, as the harness's updater did [inference from the blocking result]. The HUD's function context must stay alive while it is open, because the property table belongs to it (`S4Hud.lua:67`).
- **Still [unverified] after S4:**
  - whether the HUD takes keyboard focus when it opens (Jim clicked back into the main window before each key test);
  - buttons in a floating dialog (PRD §6.3 wants Abort / Accept / Pick / Approve, PHASES Phase 5): the spike had labels only;
  - updates driven by bridge messages rather than a timer (PHASES.md wording). The binding path is the same [inference], but the source was a timer task;
  - `presentFloatingDialog` without `blockTask`;
  - `closeFloatingDialogsForPlugin` (closing the HUD from code);
  - the HUD with a second monitor, or with Lightroom minimised;
  - repeatability: one run only.
