## Analysis (Claude Code, 2026-09-26)

Every statement below comes from the two JSON files in `docs\reports\phase0\S6\`, unless it carries another handle or tag. The runtime version is recorded this time: `lr_version: "15.5.1"` in both files (from `LrApplication.versionString()`, `S6Run.lua:94`).

- **`createVirtualCopies` works from both views: 3 of 3 copies each time** (`total_copies: 3` in both files).
  - The view is what Jim declared by choosing the menu item. The harness can only read the module, which was `"library"` both times (`current_module`), not Loupe vs Grid. That the Loupe run really ran in Loupe rests on Jim following README step 2 (press E) [inference: Jim reported "S6 done" and no deviation].
  - The old Grid-only bug (LR_SDK_NOTES LrCatalog [community]) did not show on LrC 15.5.1.
- **Each call copied the selected photo, returned the new copy, and made it the active photo.**
  - Before every one of the six calls, the harness re-selected the master (`setSelectedPhotos`, `S6Run.lua:107-109`), and `target_before_local_id` was the master (3869533) each time.
  - Each call returned a table holding exactly one photo (`returned_type: "table"`, `returned_count: 1`). That photo was the new copy: `is_virtual_copy: true`, `master_local_id: 3869533`, `file_name` the same NEF.
  - After each call the active photo (`target_after`) was that new copy, not the master.
- **The name argument becomes the copy name.** `copy_name` read back as "AVG S6 A", "AVG S6 B", "AVG S6 C", matching each call's `name`.
- **No write gate needed.** All six calls worked on the first attempt, outside `withWriteAccessDo` (`how: "outside write gate"`). The harness's fallback inside a gate (`S6Run.lua:63-76`) was never used.
- **Timing:** 1017 ms for the first call of the session (Loupe A), then 212–267 ms for the other five. Why the first call was slower is not known; a one-time warm-up is a guess [inference].
- **Every copy is addressable by `localIdentifier`, two ways.**
  - `catalog:getPhotoByLocalId` exists (`get_photo_by_local_id_exists: true`) and returned the matching photo for all six copies (`found_via_get_photo_by_local_id: true`; the harness compares the returned photo's `localIdentifier`, `S6Run.lua:143-145`).
  - The `getAllPhotos()` scan found all six as well (`found_via_get_all_photos_scan: true`).
  - This settles the pre-run conflict: LR_SDK_NOTES' `getPhotoByLocalId` [community] is present on 15.5.1. Automaat's note that `LrCatalog` has no `findPhotoByLocalIdentifier` [upstream claim] names a different function, and the scan it uses is not needed for lookup by id.
- **The copies could be selected from code for cleanup.** `setSelectedPhotos(copies[1], copies)` left exactly the three new copies selected (`copies_selected_for_cleanup: true`; `selection_after` lists the three copy ids, both runs). Jim then removed them with Remove Photos, and the original stayed (Observed).
- **In these two runs, the removed copies' ids did not come back.** The Grid run's copies got new ids (3870826, 3870860, 3870891) after the Loupe run's copies (3870730, 3870764, 3870795) had been removed. Two runs do not show that Lightroom never reuses a removed photo's id; that stays [unverified].

## Consequences / open questions

<!-- PRD §6.6 variants flow (selection guard before createVirtualCopies); Phase 4 lookup strategy. -->
Proposed changes; none has been applied to the vault docs. They are for the architect (Jim).

- **AVG-008 (Variants mode, three copies): feasible as designed.** Its handle ("spike AVG-S6 confirms behaviour on LrC 15.5.1") can now point at this report.
- **PRD §6.6 step 1 (`PRD.md:130`), variants flow.** The selection guard the PRD asks for is needed, and so is more:
  - The new copy becomes the active photo after each call [handle: `target_after` in all six calls]. The plugin must therefore **re-select the master before each of the three calls**, as the harness did (`S6Run.lua:107-109`). Otherwise the second call would copy copy A [inference: the call copies the selection, and the selection has moved to the new copy].
  - Use the call's return value to learn the new copy (one `LrPhoto` per selected photo) [handle: `returned_count: 1` each call]; there's no need to diff the catalog.
  - Pass the copy name as the argument: it becomes `copyName` [handle: `copy_name` read back].
  - No `withWriteAccessDo` around the call [handle: `how: "outside write gate"`, six of six]. Whether wrapping it in a gate would also work was not tested.
- **LR_SDK_NOTES LrCatalog (`LR_SDK_NOTES.md:34`):**
  - `createVirtualCopies(copyName)`: record as observed on LrC 15.5.1 (acts on the selection; returns the copies; works from Loupe and Grid; no write gate; the new copy becomes the active photo), instead of [community].
  - `getPhotoByLocalId`: record as present on 15.5.1 and working for virtual copies [handle: `found_via_get_photo_by_local_id`].
- **Phase 4 lookup strategy:** look copies up with `catalog:getPhotoByLocalId(id)`, not a `getAllPhotos()` scan [handle: the same field]. How fast it is on a large catalog was not measured. Because id reuse is [unverified], check the identity of a looked-up photo before acting on it, above all before removing it: it must be a virtual copy (`isVirtualCopy`), of the session's master (`masterPhoto`), with the expected `copyName` [inference; the harness reads all three, `S6Run.lua:36-43`].
- **Open for Phase 4: removing unpicked copies from code.** PRD's "Keep unpicked variants = false" (`PRD.md:94`) and MCP_TOOLS' `cleanup_unpicked_variants` (`MCP_TOOLS.md:63`) need the plugin to remove virtual copies. S6 only showed that the plugin can **select** exactly the copies (`copies_selected_for_cleanup: true`) and that Lightroom's Remove Photos then removes only them [stated]. No SDK call that removes a photo from the catalog was tested; whether one exists is [unverified]. If none exists, the fallback is "select the copies, then Jim runs Remove Photos", which conflicts with the no-modal, autonomous design. This needs a decision in Phase 4.
- **Still [unverified] after S6:**
  - the Loupe/Grid distinction itself: the harness read only the module (`library`), so the view rests on Jim's menu choice;
  - calling it with more than one photo selected (the variants flow always selects one);
  - `getPhotoByLocalId` speed on a large catalog;
  - behaviour from the Develop module (both runs were in Library);
  - whether Lightroom ever reuses a removed photo's `localIdentifier`;
  - repeatability: one run per view.
