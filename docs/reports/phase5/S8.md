# AVG-S8 — HUD buttons, focus, closing from code, shared state, settings page

## Purpose

Six questions Phase 5 needs answered in Lightroom before the settings page (PHASE5_PLAN row 3) and the HUD (rows 4-5). Questions 1-4 are the S4 leftovers [handle: `docs\reports\phase0\S4.md` "Consequences", "Still [unverified] after S4"]:

1. **Buttons.** Do `push_button`s in a floating dialog fire? Can a click start a task that reads the photo (the HUD's buttons will start a task that sends an event to the engine)? Does an `enabled` bound to a property grey buttons out and back? Does a `push_button` title bound to a property change?
2. **Focus.** When the HUD opens by itself (PHASE5_PLAN decision 6), does the keyboard stay with the main window?
3. **Close from code.** Does `LrDialogs.closeFloatingDialogsForPlugin` close the HUD?
4. **Selection.** Does `presentFloatingDialog`'s `selectionChangeObserver` fire when the selection changes (PRD 6.13 "Target changed")?
5. **Shared state.** Do a menu item, the long-running task started at load, and the Plug-in Manager section see the same module table and `_G`? (Decides how the HUD's menu items reach the bridge task.)
6. **Settings page.** Does a Plug-in Manager section save its fields in `LrPrefs`? What does a number field do with a value over its maximum? Does the running task see an edit without a restart? Are the values still there after a restart? (AVG-006, PRD 6.2, PHASE5_PLAN decision 2.)

PHASES.md gives no go/no-go rule for S8; the spike is PHASE5_PLAN decision 1, quoted: "Spike S8 before any HUD code." Claude Code's proposal for what each answer decides, for Jim to accept or change [inference]:

| Question | If yes | If no |
|---|---|---|
| 1 buttons fire, the click's task reads the photo | The HUD's buttons each start a task that sends `hud_*` to the engine (row 4) | Abort / Accept / Pick / Approve move to menu items (FR-1.1) and chat; decide before row 4 |
| 1 `enabled` binding | Pick A-C greyed until `awaiting_pick`; Approve greyed unless a step waits for it | Buttons always enabled; the engine refuses a click out of turn and the HUD says why |

| 5 module state shared (menu ↔ loop) | Menu items call the bridge task directly | Menu items leave a request file the bridge loop reads, as S8 does |
| 6 saved, seen live, kept after restart | The page as planned; the engine reads it through `get_prefs` at session start | The engine reads the page only after a restart, or the page writes a file; decide before row 3 |

How Jim answers what only he can see: tick boxes in Lightroom dialogs (menu items 1-4), the rule 04 default.

## Harness

- Plugin `plugin\spikes\S8.lrplugin`, laid out like `plugin\LrC-AVG.lrplugin` (an init script starts a long-running task; menu items reach it through a file):
  - `Info.lua`: `LrInitPlugin` + `LrForceInitPlugin`, `LrPluginInfoProvider`, four menu items (`S8Step1-4.lua`).
  - `S8Init.lua`: starts the loop, sets question 5's init mark.
  - `S8Loop.lua`: the long-running task (stands in for the bridge): reads `s8_request.txt`, opens the HUD 5 s after an "open", calls `closeFloatingDialogsForPlugin` on a "close", writes `s8_loop_view.json` every 2 s (prefs as it sees them, with the time each change reached it; the marks).
  - `S8Hud.lua`: the HUD (questions 1-4) and its result, `s8_hud_<time>.json`.
  - `S8InfoProvider.lua`: the Plug-in Manager section (question 6); writes `s8_panel_view.json` when it renders.
  - `S8Settings.lua`: menu items 3 and 4, `s8_settings_{before,after}_restart_<time>.json` plus a copy of the loop's view.
  - `S8Ask.lua` (tick boxes), `S8State.lua` (the shared module), `S8Common.lua`, `SpikeJson.lua` (a copy of S7's).
- `spikes\S8\collect.ts` copies the saved files into `docs\reports\phase5\S8\` (user folder written as `%USERPROFILE%`) and writes `s8_summary.json`.
- How to run: [`spikes\S8\README.md`](../../../spikes/S8/README.md).

Design points:
- **The HUD is opened by the loop, not by the menu item**, as the bridge task will open it (PHASE5_PLAN decision 6). The 5 s delay lets Jim click into the main window first, so the focus question tests the opening itself. Menu item 1 shows no window on success, since a window would take the keyboard [inference].
- **Nothing is written to a photo.** Each click starts a task that reads the selected photo's `Exposure2012` (the query outside any gate, the settings inside the read gate, rule 03).
- **The Approve button's bound title has a fixed "Approve:" label beside it**, so Jim can find the button even if Lightroom ignores the binding [upstream claim: `vendor\automaat\plugin\LightroomMCP.lrplugin\PluginInfoProvider.lua:760-765`, "Lightroom ignores a binding on a push_button title"].
- **`closeFloatingDialogsForPlugin` is tried with `_PLUGIN`, then with no argument**, because its argument is not documented (below). "Closed by code" is **yes** when the window closed inside the call. If it closed only after the call returned, its closing time cannot tell the call from Jim's X (Greptile, PR #40). The README has Jim watch for 10 s before using the X. Within those 10 s, Jim's tick "closed by itself" decides (no answer: **unclear**). Later than that, the result is **no**, or **unclear** if Jim ticked "closed by itself" (Greptile, PR #40 round 2).
- **A close request during the 5 s delay cancels the pending open** (Greptile, PR #40).
- **The Plug-in Manager's marks are "inconclusive", not "not shared", when they cannot be compared**: the panel file was not written (the error is kept in `prefs.s8_panel_view_error`), or the panel has not rendered since the Lightroom start the loop reports (Greptile, PR #40).
- **The settings section was rebuilt after run 1 (`fix/s8-settings`).** In run 1 it saved nothing, before or after the restart. Menu item 3 read the defaults twice (18:54 and 19:00), and no field ever passed a value to the observers that were to save it (`observed_log` null) [handle: `docs\reports\phase5\S8\s8_summary_run1.json` `settings.before_restart`, `settings.after_restart`; the run's files in `docs\reports\phase5\S8\`; stated: Jim, 2026-09-28, "I did look at them after selecting AVG S8 - 4 and they had not been saved. I don't beleive that the settings were saved at all."]. Its fields had no `bind_to_object`; that this is why they were bound to no table S8 watched is [inference], after an Adobe forum answer that a Plug-in Manager section's rows need one [community: https://community.adobe.com/questions-675/binding-problem-in-lrplugininfoprovider-sectionsforbottomofdialog-949485]. The rebuilt section shows three groups with the same two settings (Mode, Max passes 1-8), each saved another way:
  - **A:** bound to the section's property table (explicit `bind_to_object`), an observer copies each change into the prefs (Automaat's pattern with the bind object made explicit);
  - **B:** bound straight to the prefs table [community: https://github.com/kyl191/lr-stash/blob/master/PluginInfoProvider.lua];
  - **C:** bound to the property table, copied in by `startDialog` and out by `endDialog`, which run when the plugin is selected or deselected in Plug-in Manager [community: Lightroom SDK Guide, https://www.yumpu.com/en/document/view/36018599/lightroom-sdk-guide/33]; each call is logged in `prefs.s8_dialog_log`.
  - Menu items 3 and 4 are written to report each group ("saved approve_each_pass and 6: YES/NO") [handle: `plugin\spikes\S8.lrplugin\S8Settings.lua:44-46` (`groupSaved`), `:112-115` (the result lines); the smoke checks "all three groups saved", "observers silent: group A not saved, B and C saved" and "after: menu 4 reports each group" in `docs\reports\phase5\S8-smoke\smoke.txt` "Scenarios"]; that the window shows them in Lightroom is [unverified] until the rerun. Jim reruns only the settings steps (README "Settings rerun"). Run 1's "page kept the values" tick after the restart conflicts with Jim's statement above; the statement stands [stated].
- **`collect.ts` reads a JSON file again when it does not parse** (5 tries, 300 ms apart), because the loop rewrites `s8_loop_view.json` every 2 s while Lightroom runs. If the live file never parses, it is skipped with a note; the settings steps' stable copies stand for it (Greptile, PR #40).
- **Every value the settings observers receive is appended to `prefs.s8_observed`**, so the files show what a number field passed on for "12" without relying on Jim's memory.
- **Question 5 compares marks, not `_G` alone:** the loop, the menu item and the panel each write or read a random mark on `_G` and in `S8State`, and the files record which ones match.

## Pre-run findings (Claude Code)

- **SDK reference pages** [handle: lrc.mcor.dev, read 2026-09-28]:
  - `presentFloatingDialog(plugin, args)` (SDK 5.0) takes `title`, `contents`, `blockTask`, `save_frame`, `onShow`, `windowWillClose`, `selectionChangeObserver`, `sourceChangeObserver` (https://lrc.mcor.dev/modules/LrDialogs.html). **`closeFloatingDialogsForPlugin` is not on that page**; it is listed among the LR5 additions [community: LR_SDK_NOTES "LrDialogs / LrView"].
  - `enabled` is a control property: "Indicates whether the control should be enabled" (https://lrc.mcor.dev/modules/LrView%20control%20view%20properties.html). Whether it can be bound is not stated.
  - For edit fields, `precision` makes the field numeric and `min`/`max` bound it (https://lrc.mcor.dev/modules/LrView%20edit%20view%20properties.html). What happens to a value outside them is not stated.
  - `LrTasks.canYield()` "Reports whether a cooperative task is currently running" (https://lrc.mcor.dev/modules/LrTasks.html).
  - `prefsForPlugin` stores Booleans, numbers, strings and tables of them; iterate with `prefs:pairs()`; persistence across sessions is not stated (https://lrc.mcor.dev/modules/LrPrefs.html).
  - The plug-in info provider (`sectionsForTopOfDialog`) is not on the site (the LrPlugin page covers the `LrPlugin` class only, https://lrc.mcor.dev/modules/LrPlugin.html). S8 follows Automaat's section [upstream claim: `vendor\automaat\plugin\LightroomMCP.lrplugin\PluginInfoProvider.lua:678-698, 727-752`]; Automaat also says its InfoProvider module body runs again each time Lightroom renders the Plug-in Manager panel, sharing `_G` with its init script [upstream claim: same file, 46-55].
- **Lua 5.1 syntax:** 14/14 S8 Lua files parse [handle: `docs\reports\phase5\S8-smoke\smoke.txt` "Parse"].
- **Smoke run against a fake Lightroom under fengari** (virtual clock, tasks as coroutines, files in memory), nine scenarios, every check passed [handle: same transcript, "Scenarios"; its first line reads "BUILD: every run as expected."].
