## Consequences / open questions

Proposed changes; none has been applied to the vault docs. They are for the architect (Jim).

- **AVG-010 / MCP_TOOLS intent `default_camera_profile`: a profile is a pair, not a string.**
  - An Adobe Raw profile is written as `CameraProfile = "Adobe Standard"` plus its full `Look` table.
  - A Nikon Camera Matching profile is written as `CameraProfile = "<string>"` plus `Look = {}`. Without the empty Look, an Adobe Look stays applied on top.
  - Adobe Standard is `CameraProfile = "Adobe Standard"` plus `Look = {}` [inference from the Nikon test].
  - The intent should name the profile ("Adobe Landscape", "Camera Landscape") and let the params map produce the pair.
- **The engine needs the Adobe Look tables.** Only a full table was shown to work. The six tables recorded in part 2 could ship with the params map, taken from `docs\reports\phase0\S5\run2\`. They embed `ProcessVersion "15.4"` and `Version "18.5.1"`, so they may need re-capturing when Camera Raw updates [inference]. Whether `{ Name, UUID }` alone is enough stays [unverified].
- **Open question: what identifies a Look.** The evidence cuts both ways:
  - In part 2, each Adobe profile had one UUID, the same on both photos and in both recorder passes.
  - The Look named Adobe Color appeared with a different UUID in part 1 (same `LookTable`, but other fields differ and it sat over another `CameraProfile`).
  - Whether those are the same profile to Lightroom is [unverified].
  - Proposal: Phase 1 keeps `Name`, `UUID` and `LookTable` for every Look it records or writes, and doesn't treat any one of them as the identity until this is settled.
- **Read back every write** (already a part-1 consequence). Part 2 shows why: a successful `CameraProfile` write can still leave the photo on an unexpected Look.
- **Profile choice changes the picture beyond the sliders.** An Adobe Look applies its own clarity, highlights, shadows and tone curve, and none of them move the top-level sliders. PRD "every edit shows on the Develop sliders" holds for pass 1+ edits, but the pass-0 profile choice is visible only as the Profile name [inference]. The engine's metrics already see its effect, because they measure Lightroom renders.
- **AVG-005 (snapshots for rollback) is feasible as designed.**
  - `createDevelopSnapshot(name, true)` returns `true`.
  - Apply and delete take the entry's `snapshotID`.
  - The restore was exact over all 178 keys, `Look` included.
  - For LR_SDK_NOTES "To record in Phase 0": the `id` parameter of `applyDevelopSnapshot` / `deleteDevelopSnapshot` is the `snapshotID` field (`id_global` untested).
- **Lens corrections: the params map can expose both keys.** `EnableLensCorrections` (boolean) and `LensProfileEnable` (0/1) are independent. Still [unverified]: the "on" direction via `applyDevelopSettings`, and which UI control each key drives.
- **Plugin state:** in-memory `_G` state was once not visible from a different menu-item script in the same Lightroom session, cause unknown (Part 2 analysis). Candidate LR_SDK_NOTES pothole, [unverified]. Phase 1 should keep bridge state inside one long-running task, or on disk, rather than across menu scripts.
- **Still open from S5:**
  - which keys monochrome profiles drop;
  - whether `LrSdkVersion = 13.0` hides SDK 14/15 keys;
  - the cause of "Profile missing." after the part-1 writes.
- **Resolved from the handover's [unverified] list:**
  - `applyDevelopSettings` accepts a `Look` table;
  - `Look = {}` clears a Look;
  - snapshot apply/delete take `snapshotID`.
