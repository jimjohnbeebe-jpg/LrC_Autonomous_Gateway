# AVG-S10 — the rendered pipeline recorded

## Purpose

Record, from live `getDevelopSettings()` dumps and writes read back, what Lightroom Classic does with every image format it develops that is not raw: which pipeline each format is on, which keys the rendered pipeline carries and what they take, how its profiles are stored, whether a process version 11.0 photo writes like a 15.4 one, and whether virtual copies, exports and snapshots behave as on raw. The engine's Phase 0 pins (keys, profiles, ranges) all came from raw files, so a session on a JPEG fails at pass 0 (repo issue #95).

**PHASE8_PLAN row 1, quoted:** "Spike S10, the rendered pipeline recorded (the S5 pattern). (a) `npm run keys:census` … (b) … write tests on `DSC_0031 Copy 1` behind a snapshot: every canonical parameter, `IncrementalTemperature`/`IncrementalTint` with a range probe (one step beyond, as Phase 1), each recorded profile pair, `LensProfileEnable`, `WhiteBalance`; 3 the same write tests on a PV 11.0 JPEG; 4 virtual copies of a JPEG; 5 `export_preview` of each format (HDR AVIF and float TIFF included)." As built, the census is `npm run s10:check -- --fixtures` / `--census`, and the write battery runs on every photo of the collection, not two (each behind its own snapshot), so every format gets write evidence in one run [inference: the same code looped; Claude Code, 2026-10-08].

**Rule.** PHASES.md Phase 8 gives this spike no go / no-go rule. Proposed [inference]:
- **go** (row 2 pins the rendered keys, profiles and ranges; row 3 builds the pipeline into the params map) when every photo reads `PUT BACK: YES`, every rendered photo's census names the pipeline "rendered" (no "unknown"), and the rendered white-balance keys take at least one written value;
- **conditional** when a format's writes or export fail while the others work: that format is listed by name as not supported until its cause is found;
- **no-go** when the rendered keys take no write at all, or a snapshot cannot put a photo back.

**How the check asks Jim:** y/n questions in PowerShell about the selected photo (rule 04 lets Jim choose this per check; the Phase 4 WB check and the phase checks use it).

## Pre-run findings (Claude Code)

1. **Read-only probes of Jim's catalog, 2026-10-08** (scripts and outputs in `logs\nonraw-2026-10-08\`, gitignored; row 2 commits a redacted copy under `docs\reports\phase8\probes\`): one photo each of JPG, PNG, TIFF, PSD, HEIC, AVIF and a "-Rendered" DNG share one settings model with the JPG, 168 keys in common with the NEF; versus raw they carry `IncrementalTemperature`/`IncrementalTint` instead of `Temperature`/`Tint`, `CameraProfile` "Embedded" and no `Look`, and no `LensProfile*` detail keys [handle: `logs\nonraw-2026-10-08\kinds.json`, `probe-kinds.mts`]. A `.jpeg` reported `file_format` "HEIC"; DNG occurs in both pipelines [handle: `formats.json`]. JPEGs captured 2003-2013 (2 sampled per year) are on process version "11.0", whose dump has the same keys and types as 15.4 plus `AILook` and `FilterList` [handle: `probe-pv.mts` output, `pv-keys.json`].
2. **The census against Jim's live Lightroom** (`node engine\dist\devtools\s10-check-cli.js --census`, 2026-10-09T04:50Z, plugin 0.18.1, LrC 15.6): 13 photos in "fixtures", 11 raw and 2 rendered, **0 unknown**: the two pipeline signals agreed on every photo. Among the raw ones, `_DSC0028.NEF` is on process version 11.0 (173 keys), so "Version 5" is not a JPEG-only matter. The two rendered photos (`DSC_0031.JPG` Copy 1, `_OZ80660.JPG`) carry exactly `IncrementalTemperature` and `IncrementalTint` beyond the raw pin (plus `CropConstrainAspectRatio` on the cropped copy) [handle: `%TEMP%\LrC-AVG\S10\s10_check_2026-10-09T04-50-30-341Z.json`, collected into `docs\reports\phase8\S10\` with Jim's run].
3. **The session logs of the failure**: pass 0 wrote `CameraProfile "Adobe Standard"` plus a Look and read back "Embedded" and nothing; the other pass-0 writes were taken [handle: repo `logs\20261008-774c64.json`, `logs\20261008-a7ce92.json`, `failures[0].details.mismatches`].
4. **Tests**: 6 cases against the simulated plugin with the rendered dump (`engine\tests\fixtures\s10-rendered-dsc0031.json`, the settings of `DSC_0031.JPG` Copy 1 from finding 1): the pipeline rule, the census, the battery with put-back, the copies, the missing collection, a failed write put back [handle: `npx vitest run tests/s10-check.test.ts`, 2026-10-09].
5. The sim takes every numeric value and clamps nothing, so what the tests record for the range probes is the shape of the results, not Lightroom's answer.
6. **Jim's run 1 (2026-10-09, 11:55Z; `%TEMP%\LrC-AVG\S10\s10_check_2026-10-09T11-55-47-680Z.json`, collected into `S10\` with the final run) changed the harness** (`fix/s10-selected-writes`): 31 photos (13 raw, 18 rendered, 0 unknown; every Photoshop-made format read as rendered, JXL included), 30 `PUT BACK YES`. (a) On the one selected photo, 1 % past the limits was clamped or ignored as in Phase 1 and the raw "Adobe Color" pair was refused; on the 30 photos written by uuid without selecting, every out-of-range value and the raw pair read back exactly as written [handle: that file, `writes[*].range.above_max`, `writes[*].profiles.pairs[1]`]. So Lightroom checks a write only on the photo loaded in Develop, and the battery now selects each photo first. (b) On the rendered pipeline Monochrome is `ConvertToGrayscale = true` with `CameraProfile` "Embedded" and no `Look` [handle: `run1\s10_profiles_recorded_2026-10-09T04_54_46.json` key_count 154; census dump `s10_DSC_0031.JPG__AAFDE261.json`]; the recorder's key and the written pair now carry it. (c) The bridge dropped (`ECONNRESET`) on the last photo, which was not put back by the check; the harness now waits for the bridge to return before a put-back. (d) `IncrementalTemperature`/`IncrementalTint` took ±101 on unselected photos: their limits are unknown until the selected-photo run.
