# AVG-S2 — LrSocket dual socket

## Purpose

Can the plugin listen with `LrSocket.bind` `mode="receive"` on 8765 and `mode="send"` on 8766, the engine connect to both, and messages up to at least 1 MB round-trip intact? What is the RTT?
PHASES.md rule, quoted: "Go: both directions work, ≥ 1 MB messages pass. No-go: adopt HTTP polling fallback at ≤ 250 ms active."

- `plugin\spikes\S2.lrplugin\{S2Server,S2Start,S2Stop,S2Status}.lua` and `spikes\S2\client.ts`.
- `spikes\S2\summarize.ts` prints every number in this report from the collected files.
- How to run: `spikes\S2\README.md`.

## Analysis (Claude Code, 2026-09-26)

Every statement below comes from `docs\reports\phase0\S2\summarize.out.txt` or from the three files it reads, unless it carries another handle or tag.

- **Both directions work, on LrC 15.5.1 / Windows 11.**
  - The plugin listened with `LrSocket.bind` `mode = "receive"` on 8765 and `mode = "send"` on 8766. Node connected to both: the receive side at 08:58:56.536 and the send side 2 ms later.
  - All 26 messages came back intact: `hello`, 20 pings, and 1, 2, 4, 8 and 16 MiB base64 strings. 26 received and 26 echoed by the plugin, 0 failed at the client.
  - For every message, the length Lua reported (`#message`) equals the length sent.
- **Small messages: median round trip 0.32 ms** over 20 pings (range 0.26–7.30 ms). The 7.30 ms maximum is a single outlier (`ping#4`); the next slowest took 0.68 ms. The plugin log shows a 7 ms gap before that ping's echo line (08:58:57.057 → 08:58:57.064), so the delay came before the plugin echoed, on the Lightroom side [inference from the log gap].
- **1 MiB (1,048,576 chars) round trip: 31.4 ms**, payload identical.
- **No size limit was found.** 16 MiB (16,777,216 chars) passed in 827 ms. The size ladder stopped there because 16 MiB is the client's default cap (`spikes\S2\client.ts:28`), not because a message failed. LrSocket's limit, if it has one, is above 16 MiB.
- **Big messages cost more per byte.** Throughput (chars sent + echoed, over the round trip) went from 129 MiB/s at 2 MiB to 39 MiB/s at 16 MiB. Where that time goes:
  - Lua's `send()` returned within 4.5 ms even for 16 MiB, so `send()` does not wait for the transfer.
  - At least 479 ms of the 827 ms for 16 MiB came *after* `send()` returned. That time covers delivery to Node and Node's line reader; this run cannot split the two. (Lower bound = round trip minus the spacing between successive echo lines; the derivation is in `spikes\S2\summarize.ts`.)
  - The client's reader appends each chunk and rescans the whole buffer for `\n` (`spikes\S2\client.ts:41-52`), so each chunk costs more as a message grows. Automaat's engine reader has the same shape (`vendor\automaat\server\src\plugin-socket.ts:55-59`). That this is a large part of the time is [inference]; it was not measured.
- **Lightroom did not freeze.** Jim left the "Lightroom froze" box unticked [stated, recorded as `lightroom_froze: false` in the stop file].
- **Without a client, the listeners re-arm about every 10 s.**
  - Before Node connected, both sockets logged "listening" (`onConnecting`) again every 10.06–10.21 s.
  - After Node left, the receive socket did the same. (The one 11.26 s interval spans the connection itself.)
  - This matches Automaat's note of a 10 s no-client timeout on receive sockets [upstream claim: `vendor\automaat\CLAUDE.md:19`]; here the send socket behaved the same way.
  - The harness does not log no-client errors (`plugin\spikes\S2.lrplugin\S2Server.lua:121-130, 148-157`), so the error string itself (`"timeout"`?) was not recorded [unverified].
- **The send socket did not notice the client leave.**
  - The client closes both connections when it finishes (`spikes\S2\client.ts:241-243`).
  - The receive socket logged "closed" at 08:58:58.312 and went back to listening.
  - The send socket logged nothing until Stop (08:59:43.487), and the plugin still reported `send_connected: true` at Stop.
  - This matches Automaat's upstream claim that send-mode LrSocket "does not reliably notice client disconnect on Windows" [upstream claim: `vendor\automaat\plugin\LightroomMCP.lrplugin\PluginInfoProvider.lua:410-413, 558-559`]. It has now been observed once here.
- The 39.9 s from Start to connect is the time Jim took to switch to PowerShell, not a latency.

## Consequences / open questions

<!-- AVG-004 confirmed or fallback; ARCHITECTURE §3 "base64 inside the JSON line" vs temp-file path for previews. -->
Proposed changes; none has been applied to the vault docs. They are for the architect (Jim).

- **AVG-004: LrSocket dual socket is the transport.** The HTTP polling fallback is not needed.
- **LR_SDK_NOTES §LrSocket:**
  - The "conflicting claim" that LrSocket cannot act as a server (`LR_SDK_NOTES.md:25`) is resolved: it can, with `receive` + `send` binds, on LrC 15.5.1.
  - The Automaat "HTTP server on 8765 with 3 s plugin polling" entry (`:58`) is stale (as the handover already noted).
  - "To record in Phase 0: LrSocket viability and any message-size limit" (`:66`): viable; no limit up to 16 MiB.
  - Candidate potholes to add, each from this run: listeners re-arm about every 10 s with no client; a send-mode socket did not fire `onClosed` when the client disconnected; `send()` returns in milliseconds, before the transfer completes.
- **ARCHITECTURE §3, previews as base64 inside the JSON line (`ARCHITECTURE.md:64`): the size condition holds.**
  - S1's 1600 px export was 727,872 bytes, which is 970,496 base64 chars [handle: `docs\reports\phase0\S1.md:113`; 4 × ⌈727,872 / 3⌉]. That is smaller than the 1 MiB message that round-tripped in 31 ms here, about 1% of the ~2.6 s export [inference].
  - The temp-file fallback's trigger ("if LrSocket message size is capped") did not occur.
  - **Open question for Phase 1:** encoding base64 in Lua 5.1 is plain Lua (no built-in encoder), and its cost for ~730 KB was not measured [unverified]. The export already writes a JPEG to disk (S1), and the engine runs on the same machine. Passing the file path would skip the encode entirely. Both options are open; the choice is Jim's.
- **Phase 1 bridge (plugin):**
  - Re-arm listeners from the monitor loop, as the harness did; this worked.
  - Don't trust `onClosed` on the send socket. Rebind it whenever a new client connects on the receive side (Automaat's pattern, `PluginInfoProvider.lua:410-415`), and keep the heartbeat that the ARCHITECTURE §1 topology already lists for the engine's bridge (`ARCHITECTURE.md:30`).
- **Phase 1 engine reader:** scan only the newly arrived chunk for `\n`, rather than copying Automaat's rescan of the whole buffer [inference]. At preview sizes (~1 MB) this matters little.
- **Still [unverified] after S2:**
  - round trips while Lightroom is busy (an export or render running, catalog writes);
  - non-ASCII payloads: the test sent only base64 (ASCII). Lua's `#` counts bytes and JavaScript's `length` counts UTF-16 units, so they will differ for, say, accented file names. Whether LrSocket passes UTF-8 through intact was not tested;
  - more than one message in flight: the client waited for each echo before sending the next;
  - behaviour across a plugin reload or a Lightroom restart (the README's port-held case was not hit);
  - messages above 16 MiB;
  - repeatability: one run only.
